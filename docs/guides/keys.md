# Keys and certificates

A connection holds two kinds of keys. The service provider's own key pairs are generated by the package: a SAML
connection's signing key and, when assertions are encrypted, its encryption key; an OIDC connection's
`private_key_jwt` key. And a SAML connection trusts the identity provider's signing certificates, a set you add to and
remove from as the provider rotates. Every change goes through `SineMacula\Laravel\Sso\Keys\KeyService`, scoped to a
tenant, and asks for fresh authentication first (see [Fresh authentication](freshness.md)). Resolve it from the
container for each request:

<!-- snippet: tests/Integration/Examples/Keys/KeysExampleTest.php#keys-service -->
```php
$keys = app(KeyService::class);
```

## Settings

| Key                         | Default             | Env                             | What it sets                                                                                 |
|-----------------------------|---------------------|---------------------------------|----------------------------------------------------------------------------------------------|
| `keys.table`                | `sso_keys`          | `SSO_KEYS_TABLE`                | The table keys and certificates are kept in, on the storage connection                       |
| `keys.rsa_bits`             | `3072`              | `SSO_KEYS_RSA_BITS`             | The modulus of a generated RSA key: `3072` or `4096`                                         |
| `keys.certificate_days`     | `730`               | `SSO_KEYS_CERTIFICATE_DAYS`     | How long a generated self-signed certificate is valid for: `1` to `3650` days                |
| `keys.overlap_seconds`      | `604800`            | `SSO_KEYS_OVERLAP_SECONDS`      | How long a replaced key is still accepted for decryption: `0` to `7776000` seconds (90 days) |
| `keys.expiry_thresholds`    | `[30, 14, 7, 1, 0]` |                                 | The days before its end of validity a key is warned of: see [Operations](operations.md)      |
| `keys.expiry_claim_seconds` | `300`               | `SSO_KEYS_EXPIRY_CLAIM_SECONDS` | How long one reporter holds a key while it sends a warning: `1` to `3600` seconds            |

Each is read when a key is generated or rotated. A value outside its range, or anything but a whole number (or the
digit string `env()` gives for one), fails closed with a message naming its key, such as
`sso.keys.rsa_bits must be one of 3072, 4096.`, and stops the boot outside the console while a protocol is on;
`php artisan sso:check` lists each under `[keys]`. Elliptic curve keys are always generated on P-256.

## Generating and rotating service provider keys

A key's use says what it is for:

| Use                        | Protocol | Types allowed | What it does                                 |
|----------------------------|----------|---------------|----------------------------------------------|
| `KeyUse::SP_SIGNING`       | `saml2`  | RSA           | Signs the service provider's `AuthnRequest`s |
| `KeyUse::SP_ENCRYPTION`    | `saml2`  | RSA           | Decrypts the assertions encrypted for it     |
| `KeyUse::CLIENT_ASSERTION` | `oidc`   | RSA, EC       | Signs the `private_key_jwt` client assertion |

A client assertion key must fit the connection's
[`client_assertion_algorithm`](oidc-connections.md#the-client-assertion-algorithm) when it pins one: one that does not
is refused (`key_type`, `not_allowed`), before it is generated.

Each key moves through three states: `next` (published, not yet used), `current` (signing, and for encryption,
published and decrypting) and `retiring` (replaced, still decrypting until the overlap ends). A rotation without
downtime takes four steps.

### 1. Add the first key

It is generated, with a self-signed certificate for the connection, and made current at once, since the connection has
none. Name who is acting with a `SineMacula\Laravel\Sso\Administration\ActingIdentity`, for an Eloquent user its morph
class and key, which the key events carry; the use and the type are the enums
`SineMacula\Laravel\Sso\Keys\Enums\KeyUse` and `SineMacula\Laravel\Sso\Keys\Enums\KeyType`:

<!-- snippet: tests/Integration/Examples/Keys/KeysExampleTest.php#keys-add-first -->
```php
$actor  = new ActingIdentity($user->getMorphClass(), (string) $user->getKey());
$result = $keys->addNext($tenantId, $connectionId, KeyUse::SP_SIGNING, $client, KeyType::RSA, $actor);

$state = $result->key?->state; // KeyState::CURRENT
```

`$client` is the `Http\ClientContext` of the request the call is made for, which your controller builds with
`ClientContext::fromRequest($request)`; work with no request (a console command, a queued job) passes
`new ClientContext(null, null)`. Every call that counts an attempt or reports an event takes one, never reading the
request itself, and each event it reports carries the client's IP address and user agent.

The type defaults to RSA; pass `KeyType::EC` for a P-256 key where the use allows it.

### 2. Add the next key, and publish it alongside the current one

While a key is current, `addNext()` adds the new one as `next`. Both are now published, the current key first
(`KeyRing::published()`, which the connection's metadata and JWKS are built from), so the identity provider can take up
the new key before it is used. A connection has at most one `next` key of a use: adding a second is refused with
`key_state_conflict`.

### 3. Make it current

Once the identity provider has the new key:

<!-- snippet: tests/Integration/Examples/Keys/KeysExampleTest.php#keys-make-current -->
```php
$result = $keys->makeCurrent($tenantId, $connectionId, $nextKeyId, $client, $actor);

$current  = $result->key;      // the new current key
$previous = $result->previous; // the old one, now retiring, with retiringUntil set
```

The old key is `retiring` until `keys.overlap_seconds` from now. For encryption, assertions encrypted for either key
decrypt throughout the overlap, so a response in flight when you switched still completes. An overlap of `0` stops
accepting the old key at once.

### 4. Retire the old key

Once the overlap has ended:

<!-- snippet: tests/Integration/Examples/Keys/KeysExampleTest.php#keys-retire -->
```php
$result = $keys->retire($tenantId, $connectionId, $oldKeyId, $client, $actor);
```

A `next` key you no longer want can be retired the same way. The current key is never retired (`key_state_conflict`):
make another key current first.

A private key is encrypted at rest through the package's encrypter (see [Secrets](secrets.md)) and is never returned:
every result carries the key's summary, with its certificate, public key and fingerprint only.

## Trusting identity provider certificates

A SAML connection trusts a set of the identity provider's signing certificates, and a signature is valid when any of
them verifies it. When the provider announces a new certificate, trust it alongside the old one; once it has switched,
remove the old one:

<!-- snippet: tests/Integration/Examples/Keys/KeysExampleTest.php#keys-trust-certificate -->
```php
$result = $keys->trustCertificate($tenantId, $connectionId, $certificatePem, $client, $actor);

// Later, once the identity provider signs with the new certificate
$removed = $keys->distrustCertificate($tenantId, $connectionId, $oldCertificateId, $client, $actor);
```

A certificate is refused with `settings_invalid` and one violation at `certificate`:

| Code                  | Why                                                                                                         |
|-----------------------|-------------------------------------------------------------------------------------------------------------|
| `too_long`            | It is longer than 16384 bytes                                                                               |
| `private_key_refused` | It holds a private key: give the certificate only                                                           |
| `invalid_format`      | It is not exactly one PEM-encoded X.509 certificate                                                         |
| `weak_key`            | Its RSA key is under 2048 bits, or its curve is not P-256, P-384 or P-521                                   |
| `not_allowed`         | Its key is of another kind, such as DSA or Ed25519                                                          |
| `duplicate`           | The connection already trusts it                                                                            |
| `too_many`            | The connection already trusts ten certificates: remove one first                                            |
| `unsupported`         | The connection is not a SAML connection (an OIDC provider's keys come from its JWKS), or its key is not RSA |

A certificate's dates are reported, never enforced: an expired certificate is trusted and keeps verifying signatures,
since trust comes from the certificate you configured, not from its dates. Read a summary's dates, or ask
`$summary->isExpiredAt($now)` and `$summary->expiresWithin($now, $seconds)`, or run `sso:keys:expiring` on a schedule: see
[Operations](operations.md#keys-and-certificates-nearing-expiry).

Removing the last certificate is allowed; the connection then cannot complete a sign-in until another is trusted.

Distrusting a certificate is a trust change: in the same transaction it voids the sign-ins already under way through
the connection, its unfinished authorisation requests and unredeemed handoff codes, so none completes against the
certificates it started under (see [what voiding does to people signing
in](managing-connections.md#what-voiding-does-to-people-signing-in)). Trusting another certificate only adds one a
signature may verify with, so it voids nothing: trust the provider's next certificate before it switches, without
interrupting anyone. Changing a metadata signing anchor voids, as distrusting does (see
[SAML metadata](saml-metadata.md#a-metadata-signing-anchor)). Rotating the service provider's own keys voids nothing.

## Listing a connection's keys

<!-- snippet: tests/Integration/Examples/Keys/KeysExampleTest.php#keys-list -->
```php
$summaries = $keys->keys($tenantId, $connectionId); // null when the tenant has no such connection
```

Every key and certificate of the connection, by use, then current, next, retiring and the certificates, then oldest
first. Each is a `KeySummary`: its id, use, state, type and size, certificate, public key and fingerprint, validity,
when it was made current and until when it is accepted while retiring. None holds a private key.

## Results and statuses

Every change answers a `SineMacula\Laravel\Sso\Keys\KeyResult`. Check it with `isSucceeded()`, `isRefused()` and
`isInvalid()`, or match on `$result->status`:

| Status         | From                    | Carries                                                                              |
|----------------|-------------------------|--------------------------------------------------------------------------------------|
| `added`        | `addNext()`             | `key`: the key added, `current` or `next`                                            |
| `made_current` | `makeCurrent()`         | `key`: the new current key; `previous`: the key it replaced, now retiring, or `null` |
| `retired`      | `retire()`              | `key`: the key as it was before it was removed                                       |
| `trusted`      | `trustCertificate()`    | `key`: the certificate trusted                                                       |
| `distrusted`   | `distrustCertificate()` | `key`: the certificate as it was before it was removed                               |
| `refused`      | any                     | `reason`: one of the reasons below                                                   |
| `invalid`      | any                     | `reason`: `settings_invalid`; `violations`: each setting refused and its code        |

| Reason                 | Why                                                                                              |
|------------------------|--------------------------------------------------------------------------------------------------|
| `freshness_required`   | The caller did not authenticate recently enough: ask them to authenticate again, then retry      |
| `connection_not_found` | The tenant has no connection with that id (another tenant's connection is answered the same way) |
| `key_not_found`        | The connection has no key or certificate with that id, or not of the kind the operation acts on  |
| `key_state_conflict`   | The key is not in a state the operation moves it from, or another change to it landed first      |

A violation names the setting (`use`, `key_type` or `certificate`) and its code, never the value given. A refused or
invalid change writes nothing and dispatches no event.

## Fresh authentication

Adding, making current and retiring a service provider key ask for `sso.keys.rotate`; trusting and distrusting an
identity provider certificate ask for `sso.connection.trust`. Each asks once, after what was given has been checked and
before anything is generated or written, with the maximum age configured for that operation under
`freshness.max_age_seconds`. Until your application binds a freshness contract, every change is refused with
`freshness_required` (see [Fresh authentication](freshness.md)).

## Events

Each change reports what it did once it commits: `KeyAdded` for a key or certificate added (and then `KeyMadeCurrent`
for a connection's first key of a use), `KeyMadeCurrent` naming the key replaced, and `KeyRetired` for a key retired or
a certificate distrusted. Each carries the key's id, use and fingerprint, never its private key (see
[Events](events.md)).
